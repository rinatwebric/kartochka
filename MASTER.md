1. ЧТО СТРОИМ
=====================================================================================

Продавец фоткает товар на телефон где угодно — на ковре, на столе, в руке — загружает фото на сайт,
выбирает площадку (Wildberries, Ozon, Amazon) и получает:

  - готовую карточку на чистом белом фоне в нужной пропорции;
  - чек-лист соответствия регламенту площадки с числом «пройдено 9 из 10»;
  - по каждому непройденному пункту — что именно не так, замеренное значение и что сделать;
  - текст: название, описание, характеристики;
  - ZIP со всем этим, плюс публичную ссылку, которую можно кинуть кому угодно.

Позиционирование, которое нельзя терять ни в UI, ни в питче:
это НЕ фотостудия. Photoroom, Sellable, Pebblely, Flair AI, Booth.ai и Pixelcut уже делают красивое
фото товара. Мы делаем валидатор регламента с числом: «карточку, которую площадка примет с первого
раза». Красивое фото — побочный эффект, а не продукт.

Три призовых направления закрываются одним продуктом:
  - Main / overall: понятная боль, живое демо, продавец видит готовый результат.
  - Tech depth: петля верификации с порогами, детерминированная пост-обработка пикселей, eval-стенд
    с числами до/после, реестр версий промптов.
  - Open weight: muse-glimmer (открытые веса) используется как независимый судья идентичности товара.

2. ЧТО НОВОГО В v3 (усиление функционала)
=====================================================================================

По сравнению с прошлой версией ТЗ добавлено десять вещей. Каждая либо усиливает демо, либо даёт
числа, которых у конкурентов нет, либо снимает риск.

  1. Батч-режим: 5-20 фото за один прогон, общий ZIP и сводный отчёт «примут / не примут».
     Продавец живёт каталогом, а не одной карточкой. На демо это самый сильный экран.
  2. Публичная страница результата /r/<id>: открывается без логина. Судья может потыкать сам,
     а не смотреть видео.
  3. Детерминированный white-bg fixer: после генерации фон принудительно выравнивается по пикселям
     в 255,255,255 вне маски. Модель может оставить 253,253,251 — площадка такое не примет.
     Мы не доверяем модели там, где можно посчитать.
  4. Identity gate v2: четыре независимых сигнала (pHash, гистограмма HSV, SSIM по маске, вердикт
     glimmer) с весами и порогом 0.90. Плюс self-consistency: три голоса на дорогих кадрах.
  5. Fix hints: у каждого проваленного пункта не только «не пройдено», а что сделать руками
     («товар обрезан снизу — переснимите с отступом, фон не белый — переснимите на листе А2»).
  6. Стоимость и время на карточку прямо в UI: кредиты, секунды, число вызовов моделей.
     Судьи любят, когда продукт считает свои деньги.
  7. Eval-стенд: 20 тестовых фото, автоматический прогон, JSON+CSV отчёт, сравнение версий промптов.
     Это и есть «инженерная» часть заявки: у нас есть метрика, а не ощущение.
  8. Реестр промптов с версиями: каждый промпт имеет id, в отчёт пишется, какой id дал какой score.
     Регрессия видна сразу.
  9. Устойчивость: каждый шаг идемпотентен, джоба продолжается с места падения, таймауты моделей
     обрабатываются ретраем, ошибка модели не роняет сервер и не теряет фото.
 10. Наблюдаемость: /api/health, /api/stats, структурные логи одной строкой на вызов модели.

Что резать, если не хватит времени, — в разделе 16. Порядок важен: сначала 1-3, потом 6, потом 7.

5. АРХИТЕКТУРА
=====================================================================================

Главная деталь: пайплайн НЕ выполняется одним длинным запросом. На Vercel запрос живёт секунды,
а генерация картинки идёт 20-40 секунд. Поэтому один шаг = один HTTP-вызов, клиент дёргает их
по очереди и рисует прогресс.

  POST /api/jobs                  FormData: files[] + marketplace  -> { id }
  POST /api/jobs/{id}/step        { step } -> обновлённое состояние
  GET  /api/jobs/{id}             -> состояние целиком
  GET  /api/jobs/{id}/asset/{n}   -> бинарь картинки
  GET  /api/rules/{marketplace}   -> регламент
  POST /api/demo                  -> { id } готовой демо-джобы

Порядок шагов:
  inspect -> segment -> compose -> whitebg -> identity -> [ретрай compose, максимум 2] -> rules -> copy

Правила шагов:
  - шаг идемпотентен: повторный вызов перезаписывает результат, а не падает и не дублирует;
  - шаг можно вызвать с любого места: если предыдущего результата нет, шаг возвращает 409 и список
    того, что не готово;
  - каждый шаг пишет в job.json: статус, время, стоимость, ошибку;
  - ошибка модели = retry внутри шага (2 попытки, экспоненциальная пауза), потом status failed
    с человеческим текстом, фото не теряется и шаг можно повторить кнопкой.

Состояние джобы (lib/pipeline/types.ts, zod):
  {
    id: string
    marketplace: "wb" | "ozon" | "amazon"
    status: "queued" | "running" | "done" | "failed"
    step: "inspect" | "segment" | "compose" | "whitebg" | "identity" | "rules" | "copy" | "export"
    attempts: { compose: number, identity: number }
    metrics: {
      identity: number, compliance: number, retries: number, productFill: number,
      score: number, credits: number, ms: number
    }
    checklist: Array<{ id, label, ok, measured, rule, weight, fix?, reason? }>
    copy: { title, description, specs: Record<string,string> }
    assets: { source, main?, lifestyle?, detail? }
    promptIds: { compose: string, identity: string, copy: string }
    error: string | null
  }

Хранилище: Map в памяти процесса + /tmp/jobs/<id>/job.json + файлы картинок там же.
Переживать рестарт не обязано. Это осознанно и честно написано в README: за пять дней база не нужна.
Для деплоя на Vercel годится, потому что демо одно и инстанс один; если начнёт разъезжаться —
переехать на Railway одной командой, ничего в коде не меняя.

Технические грабли, которые агент должен знать заранее:
  - в Next 15 параметры роута асинхронные: const { id } = await params;
  - в роутах с sharp и fs обязательно export const runtime = "nodejs" и dynamic = "force-dynamic";
  - в next.config.ts добавить serverExternalPackages: ["sharp"];
  - ответы моделей бывают и base64, и URL — обрабатывать оба случая;
  - кнопка «шаг» должна блокироваться на клиенте, иначе двойной клик запустит два шага;
  - никакого any, никакого @ts-ignore без записи в DECISIONS.md.

7. РЕГЛАМЕНТЫ КАК ДАННЫЕ
=====================================================================================

Правила лежат в rules/*.json. В коде правил нет. Добавить площадку = добавить файл.

  {
    "name": "Wildberries",
    "source_url": "https://...",
    "verified": false,
    "updated": "2026-10-30",
    "aspect": { "target": [900, 1200], "ratio": 0.75, "min": [700, 900] },
    "checks": [
      { "id": "bg_white", "label": "Белый фон", "type": "pixels_white",
        "threshold": 0.99, "weight": 25, "fix": "Переснимите на белом листе или включите автозамену фона" },
      ...
    ]
  }

Типы проверок, которые обязан поддерживать движок:
  pixels_white      доля пикселей вне маски в диапазоне 250-255 по трём каналам
  aspect            соотношение сторон с допуском
  min_size          минимальная сторона в пикселях
  fill              заполнение кадра bbox-ом товара, диапазон
  no_text_on_main   на главном кадре нет текста, инфографики, рамок (вердикт модели + bbox)
  no_watermark      нет водяных знаков и чужих логотипов
  single_object     в кадре один товар (вердикт модели)
  not_cropped       товар целиком, без обрезки краёв (по маске, касание границ кадра)

Итог: compliance = сумма весов пройденных / сумма весов всех; score = 0-100 для человека.
`verified: false` стоит не просто так: цифры в стартовых JSON — ориентир, их надо сверить с
официальными страницами (раздел 15, пункт 4) и поставить true с датой. В UI честная подпись
«регламент проверен <дата>».

=====================================================================================
8. МЕТРИКИ, ПЕТЛЯ, ПОСТ-ОБРАБОТКА
=====================================================================================

Считается кодом, не спрашивается у модели:
  fill            площадь bbox маски / площадь кадра, норма 0.60-0.90
  bg_white        доля белых пикселей вне маски, норма >= 0.99
  aspect          из файла, норма из rules
  sharpness       дисперсия лапласиана, предупреждение если ниже порога по выборке
  borders         касание маски краёв кадра слева/справа/сверху/снизу

Identity gate (порог 0.90):
  identity = 0.35 * (1 - hamming(pHash до, pHash после))
           + 0.25 * (корреляция гистограмм HSV)
           + 0.25 * SSIM по маске предмета
           + 0.15 * (1 если glimmer сказал same=true, иначе 0)
  На дорогих кадрах glimmer спрашивается три раза, ответ большинством голосов.

Петля:
  compose -> whitebg -> identity; если identity < 0.90, перегенерировать главный кадр с усиленным
  промптом (максимум 2 ретрая), снова посчитать; зафиксировать итог и число ретраев.
  Провал не скрывается: статус done, но пункт в чек-листе красный с причиной и советом.

White-bg fixer (детерминированно, sharp):
  1) строим альфа-канал из маски с эрозией на 1-2 пикселя, чтобы не съесть край товара;
  2) всё вне альфы заменяем на ровно 255,255,255;
  3) если модель затёрла край (по SSIM), откатываем к исходнику и пишем пункт «край товара повреждён».

Cost meter: на каждый вызов модели пишем модель, мс, кредиты; сумма в metrics. В UI три числа:
соответствие, идентичность, стоимость карточки в кредитах и секундах.
